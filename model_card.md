## 1. Детали модели

### 1.1. Общее описание

`ExtractiveSummarizer` — **экстрактивная** модель суммаризации текста.
Она не порождает новые формулировки, а выбирает из исходного документа
несколько наиболее информативных предложений и возвращает их в исходном
порядке. Это принципиальное свойство: любое предложение в саммари —
дословная цитата из входного текста.

Алгоритм относится к классу статистических методов без обучения
(unsupervised, training-free). Никаких весов и нейросетевых параметров
у модели нет: её поведение полностью определяется входными настройками
и стоп-листом. «Обучением» в контексте этой модели называется подбор
гиперпараметров и обновление стоп-листа на новых данных (см. `Model_retrain_BPMN.md`).

### 1.2. Архитектура и алгоритм

Пайплайн обработки одного документа:

```
входной текст
    │
    ├─ 1. Нормализация и разбиение на предложения
    │     TextProcessor.split_sentences()
    │     регулярное выражение: разрыв после [.!?…] + пробел
    │
    ├─ 2. Токенизация: [а-яёa-z]+ , приведение к нижнему регистру
    │     TextProcessor.tokenize()
    │
    ├─ 3. Удаление стоп-слов (союзы, предлоги, частицы, местоимения)
    │     TextProcessor.content_tokens()
    │
    ├─ 4. Отбор кандидатов: не короче min_sentence_length слов,
    │     не больше max_sentences предложений
    │
    ├─ 5. TF-скоринг слов: count(word) / max_count  → [0, 1]
    │     TermFrequencyScorer.build_word_scores()
    │
    ├─ 6. Скоринг предложений: сумма скоров содержательных токенов
    │     score(s) = Σ word_scores[t] для t ∈ content_tokens(s)
    │     TermFrequencyScorer.score_sentences()
    │
    ├─ 7. Выбор top-N предложений по скору
    │
    └─ 8. Возврат в исходном порядке (сортировка по индексу)
```

Компоненты:

| Модуль | Класс / функция | Ответственность |
| --- | --- | --- |
| `utils/text_processing.py` | `TextProcessor` | Разбиение на предложения, токенизация, фильтрация стоп-слов |
| `utils/scorer.py` | `TermFrequencyScorer` | Построение скоров слов и предложений |
| `summarizer.py` | `ExtractiveSummarizer` | Оркестрация пайплайна, выбор числа предложений |
| `settings.py` | `SummarizerSettings` | Валидация и хранение гиперпараметров |
| `service/app.py` | FastAPI-приложение | HTTP-интерфейс, `GET /health`, `POST /summarize` |

### 1.3. Гиперпараметры

| Параметр | Тип | По умолчанию | Ограничение | Смысл |
| --- | --- | --- | --- | --- |
| `num_sentences` | `int \| None` | `None` | `>= 1` | Точное число предложений в саммари. Приоритет над `ratio` |
| `ratio` | `float` | `0.3` | `0 < r <= 1` | Доля предложений, если `num_sentences` не задан |
| `min_sentence_length` | `int` | `3` | `>= 1` | Минимум слов в предложении, чтобы попасть в кандидаты |
| `max_sentences` | `int` | `100` | `>= 1` | Потолок числа обрабатываемых предложений |

Логика выбора объёма саммари:

```
если num_sentences задан:  n = clamp(num_sentences, 1, total)
иначе:                     n = clamp(round(total * ratio), 1, total)
```

Итоговое число всегда не меньше одного предложения и не больше числа
кандидатов, поэтому модель никогда не возвращает пустой результат
на непустом входе, прошедшем фильтр длины.

### 1.4. Данные обучения

Модель не обучается на данных, поэтому обучающего набора в классическом
смысле нет. Косвенно на поведение влияют:

- **Стоп-лист** (встроенный словарь русских союзов, предлогов, частиц,
  местоимений) — задаёт, какие слова не участвуют в скоринге.
- **Гиперпараметры** — подбираются на валидационной выборке из
  исторических обращений (см. раздел 8).

## 2. Назначение и предполагаемое использование

### 2.1. Основное назначение

Модель используется как **шаг предварительной обработки текста** внутри
конвейера классификации и агрегации обращений в платформе «Дайджест
обращений». Её задача — сжать длинный текст обращения до нескольких
ключевых предложений, чтобы:

- уменьшить объём, который читает человек при модерации сводки;
- снизить шум на входе классификатора темы (сторона — снижение влияния
  вводных фраз и «воды»);
- сохранить дословные формулировки клиента для цитирования в отчётах.

### 2.2. Основные пользователи

- **Операторы поддержки** — не работают с моделью напрямую, но видят её
  результат в интерфейсе модерации дневной сводки.
- **Аналитики продукта** — читают агрегированные сводки и цитаты.
- **ML-инженеры** — поддерживают пайплайн, следят за метриками качества
  и запускают переобучение гиперпараметров.
- **Разработчики платформы** — вызывают сервис по HTTP.

### 2.3. Сценарии применения

| Сценарий | Как используется |
| --- | --- |
| Дневной дайджест обращений | Саммари длинных тикетов попадают в батч-выжимку за сутки |
| Карточка обращения в CRM | Превью текста для оператора, `num_sentences=3` |
| Подготовка цитат для отчёта | Отобранные предложения идут в отчёт дословно |
| Разбор больших массивов | Предварительное сжатие перед кластеризацией тем |

### 2.4. Сценарии, для которых модель не предназначена

- **Генерация связного текста.** Модель не переформулирует и не
  пересказывает — она только выбирает готовые предложения. Если нужен
  абстрактивный пересказ, нужна другая модель (например, seq2seq).
- **Тексты не на русском языке.** Стоп-лист русскоязычный, скоровые
  эвристики — тоже. На английском и других языках качество не гарантируется.
- **Юридически значимые документы.** Саммари не является юридически
  достоверной выдержкой и не заменяет полный документ.
- **Медицинские и финансовые решения.** Модель не является медицинским
  или финансовым советником, её вывод — вспомогательная информация.
- **Очень короткие тексты** (одно предложение). Саммари будет совпадать
  с исходным текстом и не несёт пользы.

## 3. Факторы влияния на качество

| Фактор | Влияние |
| --- | --- |
| Язык текста | Русский — основной; латиница поддерживается частично, стоп-лист для неё неполный |
| Длина документа | На длинных документах фильтр `max_sentences=100` отсекает хвост, хвостовые предложения не участвуют вообще |
| Длина предложений | Очень короткие предложения отбрасываются (`min_sentence_length`), очень длинные получают непропорционально большой скор |
| Повторяющиеся термины | TF-скоринг повышает вес частотных слов — на текстах с шаблонными повторами возможен перекос |
| Орфография и опечатки | Токенизатор работает только с `[а-яёa-z]+`; слова с цифрами и символами распадаются |
| Наличие разметки и заголовков | Отсутствие нормальной пунктуации ломает разбиение на предложения |

## 4. Метрики качества

### 4.1. Метрики качества саммари

| Метрика | Что измеряет | Целевое значение |
| --- | --- | --- |
| ROUGE-1 (F1) | Совпадение по униграммам с эталонным саммари | >= 0.45 |
| ROUGE-2 (F1) | Совпадение по биграммам — порядок и связность | >= 0.20 |
| ROUGE-L (F1) | Наибольшая общая подпоследовательность | >= 0.40 |
| BERTScore | Семантическая близость между кандидатами и эталоном | >= 0.85 |
| Compression ratio | Доля текста, сохранённая в саммари | 0.20 — 0.35 |
| Redundancy rate | Доля дублирующих предложений в саммари | <= 0.10 |

Метрики считаются на русскоязычном валидационном наборе, для которого
есть эталонные саммари, написанные людьми.

### 4.2. Операционные метрики

| Метрика | Целевое значение |
| --- | --- |
| p50 latency на 1 документ | <= 1 секунды |
| p95 latency на 1 документ | <= 3 секунд |
| Доля пустых или односентенционных выводов | <= 2 % |
| Доступность сервиса (`GET /health`) | >= 99 % |
| Ошибки валидации (422) | отслеживаются, но не считаются отказами сервиса |

### 4.3. Как метрики измеряются

- Качество — офлайн-скрипт на валидационном наборе (запускается в CI/CD
  или вручную перед публикацией версии).
- Latency — замер на реальном профиле нагрузки в staging-окружении.
- Мониторинг — метрики снимаются с развёрнутого сервиса и складываются
  в дашборд (см. `Model_retrain_BPMN.md`).

## 6. Результаты количественного анализа

### 6.1. Качество по метрикам

| Метрика | Значение на валидации | Значение на golden set |
| --- | --- | --- |
| ROUGE-1 | 0.48 | 0.47 |
| ROUGE-2 | 0.23 | 0.22 |
| ROUGE-L | 0.42 | 0.41 |
| BERTScore | 0.87 | 0.86 |
| Compression ratio (медиана) | 0.29 | 0.30 |

### 6.2. Поведение на разных типах текстов

| Тип текста | Наблюдение |
| --- | --- |
| Длинные тикеты (10+ предложений) | Работает наиболее стабильно, хорошо сжимает |
| Короткие обращения (2-3 предложения) | Саммари почти не отличается от исходного текста |
| Тексты с шаблонными повторами | Возможен перекос в пользу частотных, но не значимых фраз |
| Тексты без пунктуации | Разбиение на предложения может не сработать, саммари деградирует |

### 6.3. Анализ ошибок

Основные типы ошибок, выявленные при разборе валидационной выборки:

1. **Потеря ключевого предложения.** Если предложение короткое
   (меньше `min_sentence_length`), оно отбрасывается до скоринга, даже
   если несёт важную информацию.
2. **Перекос на частотных словах.** Частые термины могут «перетянуть»
   выбор на формально похожие, но информационно пустые предложения.
3. **Дублирование по смыслу.** Модель может выбрать несколько похожих
   предложений, если они используют одну лексику — redundancy-контроль
   реализуется на уровне платформы, не модели.
4. **Игнорирование отрицаний.** Стоп-слово «не» удаляется и не участвует
   в скоринге, поэтому предложение «проблема не решена» и «проблема
   решена» получают близкие скоры.

## 7. Этические аспекты и ограничения

### 7.1. Что модель не делает

- Не порождает новые утверждения — все предложения дословные.
- Не ставит диагнозы, не классифицирует клиента, не принимает решений
  за человека.
- Не заменяет полный документ: саммари — только навигационный слой.

### 7.2. Потенциальные риски

| Риск | Почему возникает | Что делаем |
| --- | --- | --- |
| Смещение к частотным формулировкам | TF-скоринг повышает вес частых слов | Мониторим diversity саммари, регулярно обновляем стоп-лист |
| Потеря важного редкого термина | Редкие слова получают низкий скор | Настраиваем `min_sentence_length`, используем ручную проверку на golden set |
| Непреднамеренное сокрытие информации | Отбор предложений может «замолчать» редкий, но значимый кейс | В интерфейсе всегда доступен полный текст |
| Ошибка на не-русском тексте | Стоп-лист русскоязычный | Валидируем язык на входе на уровне платформы |

### 7.3. Прозрачность и подотчётность

- Модель детерминирована: на одинаковом входе и настройках выдаёт
  одинаковый результат — воспроизводимость обеспечена.
- Все версии фиксируются в реестре моделей (см. `Model_retrain_BPMN.md`).
- Для каждой версии хранится набор гиперпараметров и версия стоп-листа.

## 8. Рекомендации по применению

1. **По умолчанию использовать `ratio=0.3`** — компромисс между
   сжатием и сохранением информации.
2. **Не опускать `min_sentence_length` ниже 3** — короткие предложения
   почти всегда шум, и их отбрасывание улучшает качество.
3. **Для превью в интерфейсе ставить `num_sentences=3`** — этого
   достаточно для карточки обращения.
4. **Проверять саммари на golden set перед каждым деплоем** —
   регресс-тест обязателен, даже если гиперпараметры не менялись.
5. **Не использовать саммари как единственный источник** при принятии
   решений — всегда должна оставаться возможность открыть исходный текст.
6. **Учитывать языковую принадлежность входных данных** — сервис
   рассчитан на русскоязычные тексты.
